# 高情商聊天回复助手 Web UI 桌面壳迁移执行计划

> 状态：仅计划，不执行
>
> 目标：把当前 `PyQt5` 桌面浮窗应用，迁移为“带桌面壳的 Web UI 桌面应用”，同时保留浮窗、小应用、全局热键、截图/OCR、文档处理、本地技能、本地记忆等核心能力。

## 1. 背景与结论

当前桌面版已经具备以下能力：

- 贴边浮窗入口
- 截图与 OCR
- 聊天回复生成
- 文档模式
- 分享卡片
- 本地 Skill 编辑
- Persona / Memory

当前问题不在“功能缺失”，而在于：

- `PyQt5 QWidget + QSS` 的视觉表达上限有限
- 更复杂的动效、响应式布局、设计系统落地成本高
- UI 代码与桌面壳能力耦合较深，后续大改界面不够灵活

结论：

- 不建议改成“普通网页应用”
- 建议改成“桌面壳 + Web UI”
- 迁移过程中优先保留现有 Python 能力层，不做一次性全重写

## 2. 推荐路线

### 2.1 主推荐方案

采用：

- 桌面壳：`Tauri`
- 前端 UI：`Web UI`（React / Vue 二选一，若无既有偏好，默认 `React + Vite`）
- 业务能力层：保留 Python，作为本地 sidecar/service

### 2.2 为什么推荐这条路

- 现有 OCR、文档解析、Prompt 组装、Skill、Memory 都已经在 Python 中
- 可以先替换 UI，不必先重写整个业务层
- 包体和运行时通常比 Electron 更轻
- 更适合“浮窗小应用 + 本地能力调用”的长期形态

### 2.3 备选方案

#### 备选 A：Electron + Web UI + Python sidecar

适合：

- 团队更熟悉 Node / Web 生态
- 更看重插件、调试和社区现成方案

代价：

- 包体更大
- 常驻内存更高

#### 备选 B：Qt WebEngine / QWebEngine + Web UI

适合：

- 想保留 Qt 桌面壳
- 想最小化桌面层重做

代价：

- 仍然部分绑定 Qt 技术栈
- 中长期演进弹性不如 Tauri / Electron

## 3. 迁移原则

整个迁移必须遵守以下原则：

1. 先做能力分层，再换 UI 外壳，不直接把 `PyQt` 页面逐个翻译成 Web 页面。
2. 在功能未完成对齐前，保留当前 `PyQt5` 桌面版作为可运行基线。
3. 所有桌面能力都必须通过稳定的接口层暴露给 Web UI，不允许前端直接耦合 Python 内部实现细节。
4. 先保证主链路，再追求视觉升级。
5. 切换前必须完成“功能等价矩阵”验证，而不是只看页面是否长得像。

## 4. 目标架构

建议目标目录形态：

```text
高情商聊天回复助手/
├─ apps/
│  ├─ desktop/                 # 现有 PyQt5 版本，迁移期保留
│  ├─ shell/                   # Tauri 桌面壳
│  └─ web-ui/                  # Web 前端
├─ backend/
│  └─ desktop_service/         # Python 本地服务/sidecar
├─ contracts/
│  └─ desktop-api/             # IPC / API 契约定义
├─ skill-data/
├─ doc/
└─ chat_assistant.py
```

职责划分：

- `apps/shell/`
  - 窗口创建与置顶
  - 浮窗吸附
  - 全局热键
  - 系统截图
  - 托盘
  - 剪贴板
  - 调用本地 Python service

- `apps/web-ui/`
  - 浮窗 UI
  - 结果卡片 UI
  - 文档模式 UI
  - Skill 编辑器 UI
  - Persona 设置 UI
  - 分享卡片预览与交互

- `backend/desktop_service/`
  - OCR
  - 文档解析
  - PromptAssembler
  - ERNIE 调用
  - SkillLibrary
  - MemoryManager
  - 分享卡片渲染

## 5. 功能等价范围

迁移后必须保留：

- 贴边浮窗主入口
- 热键截图
- 沉浸模式常驻屏幕上下文
- OCR 识别聊天内容
- 聊天回复生成、复制、重写、分享
- 文件导入与文档问答
- 简历分析
- 合同审查
- Skill 编辑与热重载
- Persona 与本地最近 10 轮记忆

迁移后可以优化，但不是第一优先级：

- 更细的动画
- 更完整的设计系统
- 多窗口复杂工作台
- 云同步

## 6. 分阶段执行计划

### Phase 0：立项与冻结边界

目标：

- 明确迁移不是“重做产品”，而是“重做 UI 宿主层”

任务：

- 输出功能等价清单
- 冻结 V1 必保留能力
- 决定桌面壳最终选型
- 决定 Web 前端框架
- 决定 Python sidecar 与前端的通信方式

产出：

- 迁移范围说明
- 架构图
- 功能等价矩阵
- 技术选型决议

通过标准：

- 全员对“保留什么、延后什么、放弃什么”没有歧义

### Phase 1：拆分当前 Python 业务层

目标：

- 把现有 `apps/desktop/core.py` 中可复用能力拆成纯业务模块

任务：

- 把 OCR、文档解析、Prompt、Skill、Memory、模型调用从 `PyQt` 依赖中剥离
- 把仅与桌面 UI 相关的代码留在旧桌面壳层
- 收敛出可被 sidecar 直接调用的服务接口

建议拆分目标：

- `ocr_service.py`
- `document_service.py`
- `prompt_service.py`
- `skill_service.py`
- `memory_service.py`
- `reply_service.py`

产出：

- 不依赖 Qt Widget 的 Python 能力层

通过标准：

- 业务层可以在不启动 `PyQt` 窗口的情况下独立运行

### Phase 2：搭建 Python sidecar / desktop service

目标：

- 让 Web UI 不再直接碰 Python 内部模块，而是通过服务接口调用

任务：

- 设计 API / IPC 契约
- 实现本地服务启动与关闭
- 暴露以下接口：
  - 截图 OCR
  - 文本生成回复
  - 文档解析
  - 文档问答
  - 简历分析
  - 合同审查
  - Skill 保存 / 读取 / 重载
  - Persona / Memory 读写
  - 分享卡片渲染

建议：

- 优先使用本地 HTTP + WebSocket 或标准输入输出 IPC
- 不建议前端直接读写 `skill-data/`

产出：

- `desktop_service`
- API 契约文档
- 本地调试方式

通过标准：

- 前端可在不依赖旧 `PyQt UI` 的情况下调通主能力

### Phase 3：搭建桌面壳与 Web UI 骨架

目标：

- 先拿到可运行的壳和页面骨架

任务：

- 初始化 `Tauri` 工程
- 初始化 `web-ui` 工程
- 建立状态管理方案
- 建立 UI 路由与组件层级
- 建立与 `desktop_service` 的通信适配层

Web UI 需要先落的页面/区域：

- Dock 浮窗
- 结果面板
- 文档操作区
- Skill 编辑器
- Persona 设置页

产出：

- 壳层可启动
- Web UI 可在桌面壳里运行
- 前后端可以互通

通过标准：

- 桌面壳能显示浮窗和结果面板的空骨架

### Phase 4：迁移主链路

目标：

- 优先把日常最高频链路迁完

任务顺序：

1. 浮窗显示与吸附
2. 截图入口
3. OCR -> 回复生成
4. 结果卡片复制 / 重写 / 分享
5. 热键与沉浸模式

交付标准：

- 用户可以在 Web UI 桌面壳版本里完成“截图 -> 出结果 -> 复制”

### Phase 5：迁移文档与配置能力

目标：

- 补齐非聊天主链路

任务：

- 文件拖拽与选择
- 文档预览
- 文档概括 / 提取 / 提问
- 简历分析
- 合同审查
- Skill 编辑
- Persona 设置
- 本地记忆展示

通过标准：

- 新壳版本对齐现有桌面版所有核心非主链路功能

### Phase 6：桌面能力补全

目标：

- 处理“桌面壳版本最容易翻车”的原生能力

任务：

- 多屏截图
- DPI 缩放
- 剪贴板图片/文本
- 全局热键冲突处理
- 窗口置顶与焦点策略
- 自动更新策略
- 打包与签名

通过标准：

- 在目标操作系统上稳定运行，不因为截图、热键、缩放而频繁崩

### Phase 7：灰度切换与旧版退场

目标：

- 有序完成版本替换，而不是强行切换

任务：

- 保留 `PyQt5` 版作为 fallback
- 增加运行时切换开关
- 进行小范围试用
- 收集异常日志
- 修复阻塞问题
- 再决定是否下线旧版

切换建议：

- 第一阶段：双轨并行
- 第二阶段：新版本默认，旧版本保留
- 第三阶段：确认稳定后再删除 `PyQt5 UI`

## 7. 核心技术决策清单

迁移前必须明确的事项：

1. `Tauri` 还是 `Electron`
2. `React` 还是 `Vue`
3. Python sidecar 的启动方式
4. IPC 选本地 HTTP / WebSocket / stdio
5. 分享卡片渲染放 Python 还是前端 Canvas
6. 截图能力放桌面壳还是 sidecar
7. 热键失败时的降级策略
8. 安装包和自动更新方案

建议优先决策：

- 桌面壳：`Tauri`
- 前端：`React + Vite`
- Python sidecar：独立本地服务进程
- IPC：本地 HTTP + 明确 JSON 契约
- 分享卡片渲染：前端 Canvas 为主，Python 渲染为兼容 fallback

## 8. 风险清单

### 风险 1：迁移过程中功能短期倒退

典型表现：

- UI 更漂亮了，但热键、截图、贴边、剪贴板不稳定

应对：

- 先做功能等价矩阵
- 保留 PyQt 版直到 Web UI 版达标

### 风险 2：Python sidecar 与桌面壳通信不稳定

典型表现：

- UI 有了，但请求链路脆弱，启动顺序复杂

应对：

- 先把 API 契约固定
- 先做本地服务健康检查与重连机制

### 风险 3：作用域失控

典型表现：

- UI 迁移过程中顺手改产品逻辑、模型逻辑、文档逻辑，导致工期爆炸

应对：

- 迁移期只做架构替换和必要重构
- 新需求一律进后续 backlog

### 风险 4：多平台桌面能力难度被低估

典型表现：

- 浮窗、截图、热键在不同系统下行为不一致

应对：

- 先以 Windows 为第一目标平台
- 其他平台另开兼容计划

## 9. 验收标准

只有当以下条件同时满足，才允许进入切换阶段：

- Web UI 桌面壳版本可以独立启动
- 浮窗、热键、截图、OCR 主链路可用
- 文档模式、简历分析、合同审查可用
- Skill / Persona / Memory 可用
- 分享卡片可复制到系统剪贴板
- 至少完成一轮真实办公场景试用
- 没有 P0 / P1 阻塞问题

## 10. 推荐执行顺序

推荐顺序如下：

1. 先冻结范围
2. 再拆 Python 业务层
3. 再搭 sidecar
4. 再搭 Web UI 壳
5. 再迁主链路
6. 再迁文档和配置功能
7. 最后做灰度切换

不推荐的顺序：

- 先把页面全画出来，再补桌面能力
- 先删掉 `PyQt5` 版本，再逼自己迁移
- 一上来就把 Python 业务层也改写成 Node / Rust
